Я так понял тут предполагается принцип "golden signals" от google (latency, traffic, errors, saturation)?

http запросы, код ответа, доступность эндпоинтов - показывает, работает ли платформа для клиента.

кол-во запросов в секунду (RPS) - показывает фактический трафик.

время ответа (можно даже нормализованное по p50/p95/p99) - ресурс может быть доступен, но отвечать слишком долго.

ошибки (прежде всего 5-сотые) - показывает сбои вычислений, нехватки ресурсов, проблемы с зависимостями.

загрузка CPU - показания загрузки общей, по ядру, очередей, узкого места, конкуренции за ядра (iowait, load average,steal time).

storage - заполнение, наличие свободного места, I/O errors, read-only remount, inode, задержка и утилизация (await, latency, %util, очередь).
- Наличие свободного места не гарантирует успешную запись.
- При заполнении фс сервис начнёт выдавать ошибки или терять результаты.
- Множество небольших текстовых отчётов может исчерпать inode.
- Медленная запись увеличит время выполнения запросов и приведёт к росту latency.

2.
Предложу отдельный дашборд построенный на SLI/SLO в юзер френдли стиле, с рюшечками. Старый оставлю себе или инженерам.
Менеджер будет видеть:
- Долю успешных запросов + расчёт за период. напримеруспешные запросы / валидные запросы * 100% = доступность. Это дасть ответ что то на подобии 99,99% успешных расчётов за 30 дней.
- Скорость. Доля отчётов сформированных быстрее регламентного, например 90% отчётов сформированы быстрее чем за 30 сек.
- Кол-во клиентских ошибок. число неуспешных расчётов/запросов в абсолютных значениях и/или процентах. Можно сюда ещё 4-сотые прикрутить, но мне кажется это отдельная метрика некорректных действий клиента, а не отказ платформы.
- Нагрузка. Но в виде "Очередь расчётов: 10 задач", "В обработке: 15 задач", "Среднее вемя ожидания: 2 мин".
- Бюджет ошибок. Сколько допустимого ухудшения качества сервиса уже потрачено.

SLI - измеряет качество.
SLO - задаёт целевое значение (внетренняя операционная цель).
SLA - последствия за нарушение (договор с криентом).

5.
pull - система мониторинга опрашивает своих агентов по расписанию.

Плюсы:
Легкий контроль.
Проще обнаружить отклонение.
Можно в ручную проверить метрики.

Минусы:
Серверу нужен доступ к агентам.
Короткоживущий процесс может завершиться до опроса.
Ухудшение ИБ за счёт обязательных открытых портов.
Усложнение маршрутизации структуры.
Требует продуманной сетевой связности, а в изолированных сегментах может понадобиться proxy, agent active checks или gateway.


push - агенты самы отправляют метрики в систему сбора.

Плюсы:
Подходит для конвееров и быстрых задач.
Агент сам инициирует соединение, что упрощает маршрутизацию.
Повышает ИБ (или не ухудшает), может в сегментацию сети.

Минусы:
Сложно отличить "нет метрик" от "агент недоступен" или "агент мёртв".
Сложность в управлении агентами.
Возможны дубли или потери метрик при проблемах в сети.
Может накапливать устаревшие данные.
Не рекомендуется оставлять без TLS, аутентификации и ограничений, иначе любой клиент сможет отправлять ложные метрики.

9.
в `telegraf.conf` отредактировать:
```
[[inputs.docker]]
#  endpoint = "unix:///var/run/docker.sock"
#  container_names = []
#  timeout = "5s"
#  perdevice = true
#  total = false
  endpoint = "unix:///var/run/docker.sock"
  timeout = "5s"
  perdevice_include = []
  total_include = ["cpu", "blkio", "network"]
```

Выясни `GID` для `docker.sock`:
```
stat -c 'GID=%g MODE=%a OWNER=%U GROUP=%G PATH=%n' /var/run/docker.sock
```

в `docker-compose.yml` добавить привилегий для `telegraph` и добавление в группу `sock`:
```
  telegraf:
    build:
      context: ./images/telegraf/
      dockerfile: ./${TYPE}/Dockerfile
      args:
        TELEGRAF_TAG: ${TELEGRAF_TAG}
    image: "telegraf"
    user: "0:0"
    group_add:
      - "134"
    entrypoint: ["/usr/bin/telegraf"]
    command: ["--config", "/etc/telegraf/telegraf.conf"]
    environment:
      HOSTNAME: "telegraf-getting-started"
    links:
      - influxdb
    volumes:
      - ./telegraf/:/etc/telegraf/
      - /var/run/docker.sock:/var/run/docker.sock
    depends_on:
      - influxdb
```

Пересоздать `telegraph` контейнер:
```
docker compose --env-file .env up -d --force-recreate telegraf
```

Проверить:
```
docker compose logs --tail=100 telegraf
```
- в логах не должно быть `E!` и `permission denied`.
- Нужно подождать 30 сек, пока DB поднимется.
